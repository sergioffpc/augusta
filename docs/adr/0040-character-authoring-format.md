# Character Authoring Format & Packing

A player character is authored as its own folder under `<assets-root>/authoring/characters/`, holding one USD stage always named `character.usda` regardless of the folder's own name — the same fixed-name rationale as `map.usda` (ADR-0015): renaming a character never means renaming the file inside it. For the same reason the stage's default prim is always named `Character`, and its visual mesh is the child prim `Visual`: the client finds a character's mesh at `<character path>/Character/Visual` (e.g. `characters/player/Character/Visual`) knowing nothing about the stage but its path, and the cooker refuses a character stage whose default prim is named otherwise. Unlike a scenario, a character folder has no `parameters.lua` and is never itself the argument the cooker (`augustap`) takes; it's shared authoring content every scenario draws on, not scenario content. This follows CONTEXT.md's own line between the two: "Map" is the static space a match is played in — collision, spawn points, hitboxes — and a player character is an ECS entity, not scene content, so it doesn't belong inside `map.usda` alongside the level.

Characters are authored in USD, same toolchain and rationale as ADR-0016: Composer for assembly, Adobe's USD-Fileformat-plugins composing any glTF/FBX/OBJ source as a USD layer rather than a second import path. Mesh geometry follows the exact `UsdGeomMesh` → meshoptimizer path ADR-0016/ADR-0031 already define. Skeleton/skinning would be UsdSkel once that pipeline exists; this ADR doesn't resolve the runtime skeletal-animation format itself (still open — `animation.h`'s own note that this project has no character/skeleton data format yet) or how the cooker would read UsdSkel — only where the source lives and that it stays USD, so today's mesh-only character content already has a home to cook from.

The cooker keeps its existing one-argument-per-run shape (`augustap <scenario>`, ADR-0030). Addressing stays collision-free without a new indirection layer (ADR-0018 already rejects that kind of layer): a character's blobs are addressed by path relative to `authoring/` (e.g. `characters/marine/Mesh`), the same convention ADR-0031 already uses for scripts (path relative to the scenario folder). A scenario's own content is addressed by prim path relative to its own stage root and never carries a `characters/` prefix, so the two namespaces can't collide by construction. Client/server split follows ADR-0019's existing rule unchanged: mesh/texture data is client-pack-only, hitbox geometry ships to both packs — the server needs it for hit detection, same as level collision.

**Superseded by ADR-0041**: this ADR originally had every cook run walk `authoring/characters/` unconditionally and fold every character it finds into every scenario's pack, with no binding step - see that ADR for why an explicit per-scenario `characters` list (`manifest.yaml`) replaced it once one shared character stopped being the only case worth designing for.

## Considered Options

**Per-scenario explicit character binding** (a manifest, or a USD reference in `map.usda`, naming which characters that scenario pulls in, so the cooker packs only those): originally rejected here for the same reason ADR-0031/ADR-0032 already rejected an authored stable-ID indirection layer — a convention to design and maintain for a pack-bloat problem that didn't exist yet with one shared character and one example scenario. Adopted in ADR-0041 once that stopped being true.

**Characters cooked into their own separate pack, loaded by the runtime alongside the scenario's client/server pack**: rejected. The runtime (`Pack::Load`/`ResolveMesh`, etc.) only ever resolves paths inside one already-verified pack; multi-pack loading and cross-pack resolution would be a real, currently-undesigned change to that runtime surface, for no benefit at this scale over just merging everything at cook time.

**glTF as the character authoring format instead of USD**: rejected — reopens exactly the "parallel import path" ADR-0016 rejected Assimp over. USD-Fileformat-plugins already let a glTF/FBX source compose as a USD layer without a second pipeline, so there's no format-support reason to leave USD for characters specifically.
